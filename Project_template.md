# Задание 1. Исследование моделей и инфраструктуры

## Сравните LLM-модели 

### Облачные модели 

 - Простота интеграции через API
 - Нет ограничений "по железу"
 - Меньше галюцинаций
 - Высокая стоимость токенов
 - Данные компании выходят "за контур"
 - Привязка к вендору
 - Скорость работы зависит от сетевых соединений

### Локальные модели

 - Персонализированая модель, которую можно дообучить под нужды компании и внутренню терминологию
 - Данные остаются в контуре компании
 - Фиксированная цена в месяц (зависит от оборудования)
 - Скорость работы ограничена мощностью оборудования, сетевых издержек нет
 - Более сложная (относительно облачных моделей) интеграция
 - Первичные затраты на инфраструктуру, виртуальный сервер, GPU

-----

## Сравнение моделей эмбеддингов

### Облачные OpenAI Embeddings 

- Наличие лимитов (rate limits), возможно долгое ожидание при добавлении данных
- Лучше для длинных текстов и мультиязычности
- Оплачивается каждый токен

### Локальные Sentence-Transformers

- Нет лимитов, скорость создания индекса зависит от мощности оборудования, виртуальные машины используются и оплачиваются только в прцоессе индексации 
- Лучше для точного поиска, в т.ч. для специализированных терминов
- Оборудование оплачивается по фиксированной цене, токен фактически бесплатный

## Сравнение векторных баз ChromaDB и FAISS
| Характеристика | ChromaDB | FAISS |
| :--- | :---: | :--- |
| Скорость поиска при одном запросе | 0.2 мс | 0.8 мс |
| Скорость поиска при 10 конкуретных запросах | 652 QPS | 423 QPS |
| Скорость индексации 20k векторов | 0.024 сек | 2.8 сек |
| Сложность внедрения и поддержки | сложная, требует компиляции, выбора типа индекса, ручная работа с индексами и мета-данными | простая: pip install, запуск docker-контейнера |
| Удобство в работе | Среднее: больше кода, "ручная" фильтрация |  Высокое: встроенные фильтры, понятный API |
| Стоимость владения (учёт инфраструктуры) | Средняя-высокая, для полноценной работы необходим GPU | Низкая, не требует GPU, может работать на относительно слабых ВМ | 


## Возможные конфигурации

| EC2 Instance | CPU | RAM | GPU | База данных | Комментарий |
| :--- | :---: | :---: | :---: | :--- | :--- | 
| c6i.2xlarge  | 8 vCPU  | 32 GB | - | ChromaDB (персистентный режим) | Подходид для разработки  и проверки гипотез     |
| c6i.2xlarge  | 8-16 vCPU | 64 GB | NVIDIA L4 / A10G | ChromaDB (в режиме сервера) | Оптимальный вариант по цене качеству для <= 10 одновременных пользователей (без использования очередей) |
| EC2 p4d.24xlarge (A100) или p5.48xlarge (H100) | 32+ vCPU | 128-256 GB | NVIDIA A100 40GB или H100 80GB | ChromaDB (кластер) | Потенциальный вариант для миграции при нагрузке <= 50 одновременных пользователей | 

### Выводы

В данный момент оптимальным решением является использование локальных моделей с применением ChromaDB и EC2 инстансом c6i.2xlarge с GPU NVIDIA L4 / A10G. Такой набор позволит оптимально с точки зрения как финансовых и трудо-затрат начать внедрение LLM в инфраструктуру компании. 

В качестве эмбеддинг модели можно выбрать multilingual-e5-large-instruct, как модель, поддерживающую русский язык, имеющую не очень большой размер (~1.1 Gb) и способную запуститься локально.
